Bug 1 -- the leak

The first bug is about some insane shit in MariaDB called a `multipolygon`, which is apparently used to keep track of geographic areas. This is a niche, pretty absurd, complex subsystem in an already large program, so it makes sense that a bug has fallen through here. It is a nice, small lesson about where to look for these sort of bugs: if there's some absurd shit like `multipolygons` in a program you're auditing there's probably something worth poking at.

Simply put, a multipolygon is a simple data structure consisting of a binary header followed by a number of polygons. This binary header contains information about the number of polygons contained within the multipolygon itself. When we want to calculate the multipolygon's area, we iterate over that number, as stated in the multipolygon header.

Hopefully it should be obvious where this is going. When we trigger an area calculation, there is no check on whether or not the multipolygon actually has the number of polygons stated. We can construct a multipolygon that claims to have two polygons, but actually just has one. This causes our area calculations to try to parse adjacent heap data (pointers, etc.) as polygon information -- the resulting area value may, therefore, encode heap pointer information somehow!

I think this bug is actually really cool in the way that it manifests. The read isn't direct, and it is sort of type-confusiony. To get a more reliable read, we do need fine-grained control over the polygon data we send. Let's first explore how polygon data is actually stored on the heap, and what might be adjacent to our controlled polygon data. We can do this by taking a look at how v12 does it first: it does this by creating a table with three columns. The first two columns are binary data that eventually get parsed as polygon data, and then the third column is a pointer to a BLOB object on the heap (right now, this is all "A"s). The exact query is shown below.

      8   │   cy.execute("DROP TABLE IF EXISTS lk")
      7   │   cy.execute("CREATE TEMPORARY TABLE lk(a VARBINARY(74), b VARBINARY(66), c BLOB)")
      6   │   cy.execute("INSERT INTO lk VALUES (0x%s,0x%s,0x%s)"
      5   │   │           % (_GEOM74.hex(), bytes(b).hex(), payload.hex()))
SQL query that creates the malformed multipolygon. `_GEOM74` and `b` are prewritten structs from v12 (our headers), which control (among other things) the number of points in each polygon.

v12's exploit actually gave me some helpful structs, `_GEOM74` and `b`. `_GEOM74` is the malformed multipolygon header, which tells MariaDB there are two polygons within the multipolygon.. It also contains a simple polygon with three points, all at 0 (this means that its area is also 0!). `b` is an 'incomplete' polygon whose header states it has four points, but it only contains three points worth of data. The first two points are at 0, but the last point is at (1e300, 0). Because there are four points stated but only three points speciifed, the adjacent column `c` (our heap pointer) will become that fourth point.

These are all contiguously laid out as adjacent fields on the heap. By viewing the heap directly, we can see the general structure of the polygon data: there is some (unhelpful for our case) header information, then the vertices of each polygon are just stored as adjacent (x,y) QWORD double pairs.


Heap layout. Note the correspondence with the above query: polygon 1 is the 'A' column, polygon 2 is the 'B' column, and our heap pointer is C. Naturally, they are all adjacent!

First of all: pretty. Second of all, what is relevant here is the correspondence between our heap view and the actual (x,y) pairs that the area calculation takes into account. Note that there are two (0, 0) points, but there is a point at ([LARGE VALUE], 0) and ([[BASICALLY 0], [HEAP POINTER]). We can draw this out.


Our simple polygon is actually just a triangle!

So, our polygon is actually just a triangle, with the base being our large value (1e300) and our height being the heap pointer parsed as a double. Note one thing about heap pointers and doubles -- an ordinary pointer parsed as a double is actually quite small (1e-280 or so). Therefore, we need this large 1e300 value to 'amplify' this value such that we can read it properly. In general, we also need this large point placed directly before our leaked point, because of the way that MariaDB calculates area (specifically, it uses the shoelace formula, which takes in adjacent points clockwise and sums up a specific product of the two points -- this is not necessary to understand the exploit).

As expected, this leaks the pointer to our blob nicely. We just need to get the area and 'undo' the simple arithmetic (multiply by two, divide by 1e300).

[!] leaking payload
  SQL ▶ SELECT ST_Area(a) FROM lk WHERE b IS NOT NULL AND c IS NOT NULL
  SQL ◀ 1 row(s): (3.240693733576871e-10,)
leaked address: 0x774fd3fe7738
Successful leak (MariaDB client view).

Neat! We can now leak adjacent pointers. The natural next step is to then leak PIE, but this proves to be a far harder challenge. We leaked a heap pointer because placing a BLOB entry next to our malformed polygons directly inserts a heap pointer adjacent to the polygon data, but we have no such luck for a PIE pointer -- there is no datatype we could place that would just happily insert one of these PIE pointers where we want.

If we cannot place a PIE pointer in our table, the next idea is then to place a PIE pointer in an adjacent or nearby chunk to our table. The chunk where our polygon data is placed is an `0x2000` sized chunk. If we can somehow get another chunk near that chunk we can control with a PIE pointer, and just make the polygon consume a bunch of points, perhaps this will still work to leak that PIE pointer?


Potential chunk layout

This of course comes with its own issues. We would need to get this chunk layout in the first place, we would need to find a fixed-size allocation chunk with a known PIE pointer at a certain offset, and we would need to control the data before that PIE pointer (remember, we need to place an (1e300, 0) point directly before it!)

Furthermore, a natural question is: If we can't control any of the garbage in between our polygon headers and our PIE pointer, how do we know that this data won't affect our area calculation? That garbage still gets parsed as polygon points! The trick is, it just so happens that the typical garbage left inside chunks (pointers, small integers, strings etc.) are typically very small values when parsed as doubles (on the order of 1e-300). Thus, very very fortunately, it is likely that they are so small (especially when we multiply two of them together) that they underflow to 0 during the area calculation and don't affect the area calculation at all.

This, to me, is really ridiculous, but it works, apparently! Note the following two examples, where I show the average contents of a freed chunk, and the corresponding doubles they get parsed to.

This means that we have some flexibility with leaking PIE. We just need a PIE pointer somewhat close to our initial polygon header, and then configure our polygon to consume a few more points (maybe 1000 or so). Hopefully, the values in the middle will reduce themselves out to 0, and we can leak our pointer (and just our PIE pointer)!

Because they are so tiny, the polygon we calculate simplifies exactly down to our target triangle. We can have a thousand of those tiny points, but they contribute exactly 0 area to the end result: meaning, we can recover the value of our leaked pointer to 100% accuracy.

However, we still do not have a suitable target here. We can theoretically perform our leaks, but we do not have a chunk in mind that we can use to perform the PIE leak. Recall our constraints on this target chunk: we need to be able to control the data prior to the PIE pointer exactly, and we need to be able to allocate it easily. This will be detailed in the following section.

Second bug -- UAF with SYS_REFCURSOR objects

The second bug is a UAF with SYS_REFCURSOR objects. The gist of this bug is that these objects are stored in a dynamically sized array which is occasionally `realloc()'d` when more objects are appended. As we all know, `realloc()` can operate in one of two ways: consolidating adjacent freed chunks to create a larger contiguous space, or simply just freeing the old, small chunk and allocating a newer, bigger chunk. For our use case, the program will almost always take the latter path (that is, freeing the old chunk and allocating another).

The dynamic arrays happen to grow according to powers of two. This means that if we allocate 15 SYS_REFCURSORs, the dynamic array they are stored inside can still fit another SYS_REFCURSOR object (the 16th), but if we attempt to add a 17th object, the `realloc()` will occur. Similarly, if we keep allocating until our array contains 32 SYS_REFCURSORs, no `realloc()` will occur, but another (the 33rd) and it will.

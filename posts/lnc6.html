The decompilation is quite simple. There is an `fgets()` call, and then a conditional that branches off of that `fgets()` call which dictates whether or not we print the Wrong Flag message or the Correct Flag message. Interestingly, however, these flag checks are only constrained on the first 3 bytes of our input, and even more interestingly, these checks are actually impossible to pass. If we take the decompilation at face value, there is no input that would result in the Correct Flag message being printed.

The trick here is that we are hiding control flow via `libc` constructor calls and exit handlers. Constructors are a special kind of function that are called before `main()` is called. It's a nice way to 'smuggle' in function calls, because they don't typically show up in a control flow graph, and simply running `start` in a debugger will skip over them.

We can view them in the `.init_array` section of our binary - there is one standard constructor (I have labelled it `default_ctor`), and a special constructor planted artificially (`special_ctor`). Here is the source for that constructor.

   22   void __attribute__((used, constructor)) corrupt_exit_handler(void) {
   21   │ stack[0x0] = (ull)&payload_1;
   20   │ stack[0x1] = (ull)&payload_2;
   19   │ stack[0x2] = (ull)&payload_3;
   18   │ stack[0x3] = (ull)&payload_4;
   17   │ ull p = (ull)&puts - 0x82080 + 0x1e6c08; // libc base
   16   │ ull exit_handler = (ull)&puts-0x82080 + 0x1e7680;
   15   │ ull exit_funcs = *(ull*)exit_handler + 0x18;
   14   │ ull x = *(ull*)exit_funcs;
   13   │ ull q = *(ull*)p - 0xbef0 + 0x332a0; // ld base
   12   │ ull r = *(ull*)q - 0x11e0 + 0x770; // tls base
   11   │ ull s = *(ull*)r; // ptr mangle cookie
   10   │ *(ull*)exit_funcs = encrypt_ptr(s, (ull)gadgets);
    9   }

Note the `__attribute__`s here that specify this function as a constructor, such that it lands in `.init_array` at compile-time. This function loads the addresses of four different `payload`s (more on these later) to a variable named 'stack', reads some function pointers and offsets to calculate the address of `ld` and subsequently `tls`, zeroes out the `PTR_MANGLE` cookie and then corrupts the exit handler to point to a custom `gadgets` function.

This may all be unusual to the uninitiated, but this is a very standard `www2exec` technique in pwn known as exit handler corruption. When `exit()` is called in a binary, an exit handler is called and executed. The pointer to this exit handler is encrypted and stored in a writable region of memory, so if we just hijack that function pointer we can redirect execution flow to wherever we want (more details on the technique here). Again, the purpose of this nonsense is to defeat control flow graph analysis and secretly smuggle in function calls that are hard to detect statically. We are trying to obfuscate our quote-unquote 'malicious payloads'.

Of course, this is all useless if we don't know what the payloads are. All this exit_handler stuff does is redirect execution to something called `gadgets`. `gadgets()` is a very simple function here.

   11   void __attribute__((naked)) gadgets(void) {
   10   │ __asm__(
    9   │ │ ".intel_syntax noprefix\n"
    8   │ │ "lea rsp, [rip+stack]\n"
    7   │ │ "ret\n"
    6   │ );
    5   }

From now on there is going to be a lot of inline assembly nonsense, as well as naked functions (functions that do not have the `pop rbp` prologues and epilogues). Unfortunately, the style of rev I like to write is needlessly minute and tedious, and requires fine-grained control over the specific instructions executed that are simply infeasible to get with writing C alone. I think I should inevitably learn how to write an LLVM pass, that seems fun!

Anyways, all this function does is change `rsp` to point to the stack variable and then call `ret`. This means that all the function pointers stored in the `stack` variable (as we recall, `payload_1 - payload_4`) will eventually get called once the `ret` instruction fires. This is another nice obfuscation method to once again defeat CFG analysis. Let's now go over the payloads, jumping to `payload_3` because that's the more interesting function.

Obviously, if all we wanted to do was to solve the challenge, we'd just dump the encrypted buffer and xor it with 0x99. In fact, you can cheese this quite significantly by staring at the decompiled subroutines in IDA, finding the strange compares + encryption routines and just breakpointing there and sidestepping the exit handler stuff entirely, which is what I imagine a lot of AI agents + people did. But that is ok, the encryption is not interesting enough to deserve respect anyway.

I did, however, write the assembly to specifically defeat `xref`-based analysis. I did not want someone to look at the branches, see that the offsets are referenced in another block of code in a decompiler, and then just jump to that offset. How was this achieved? Laboriously, in the first two payloads!

   21   void __attribute__((naked)) payload_1(void) {
   20   │ __asm__(
   19   │ │ "lea rax, [rip]\n"
   18   │ │ "mov rbx, rax\n"
   17   │ │ "add rax, 0x2e58\n"
   16   │ │ "add rbx, 0x2cf8\n"-
   15   │ │ "mov QWORD PTR [r12], rax\n"
   14   │ │ "mov QWORD PTR [r12+8], 0x99\n"
   13   │ │ "ret\n"
   12   │ );
   11   }
   10   
    9   void __attribute__((naked)) payload_2(void) {
    8   │ __asm__(
    7   │ │ "lea r13, [rip]\n"
    6   │ │ "mov r14, r13\n"
    5   │ │ "sub r13, 0x232\n"
    4   │ │ "sub r14, 0x1dc\n"
    3   │ │ "ret\n"
    2   │ );
    1   }

The first payload dumps our XOR-key at `r12`, while the second payload loads in `rip` and manually adds / subtracts to that address to achieve offsets at our desired addresses in `main`. The end goal of this is that there are no direct references to the branches during static analysis, as these relevant addresses are computed dynamically. Note that the offsets are all hard-coded, meaning I had to calculate them manually, and every time I slightly changed the binary I would have to recompute them.

closing thoughts

My overall thoughts on this challenge is that there is a lot of wasted potential and it is way too cheeseable :( I would have made this a lot more interesting now... oh well. The issue with these sorts of challenges, where control flow is cleverly smuggled through some unpacking mechanism or some quirk, is that you very rarely even have to understand the quirk to solve the challenge. And if the quirk is where all the sauce is, then... it makes for a boring experience! The unpacking mechanism should be intricately weaved into the program somehow, such that an understanding of it is required to parse the inner workings of the binary, but indeed, this is a lot easier said than done.

Oh well! I hope this writeup was of some interest to you, at least. Learn from my mistakes!

rev - let's go gambling

I wanted to make a challenge that is theoretically solvable just by doing nothing. Indeed, if you run the binary enough times, the flag will come out. It's just infeasible to run it that many times (2 ** 500, I think).

   30   void recurse(char* flag, int i) {
   29   │ if (i > 53) {
   28   │ │ printf("FLAG CALCULATED: %s\n", flag);
   27   │ │ return;
   26   │ }
   25   │ pid_t pid = fork();
   24   │ if (pid == 0) {
   23   │ │ int p[2];
   22   │ │ char c[1];
   21   │ │ pipe(p);
   20   │ │ pid_t pid_child = fork();
   19   │ │ if (pid_child == 0) {
   18   │ │ │ encrypt(rand() & 0xFFFF, encs[i], ENC_LEN);
   17   │ │ │ void *mem = mmap(NULL, 0x100, PROT_READ | PROT_WRITE | PROT_EXEC, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
   16   │ │ │ memcpy(mem, encs[i], ENC_LEN);
   15   │ │ │ close(p[0]);
   14   │ │ │ dup2(p[1], 1);
   13   │ │ │ close(p[1]);
   12   │ │ │ payload_t shellcode = (payload_t)mem;
   11   │ │ │ shellcode();
   10   │ │ │ exit(0);
    9   │ │ } else {
    8   │ │ │ close(p[1]);
    7   │ │ │ waitpid(pid_child, NULL, 0);
    6   │ │ │ read(p[0], c, 1);
    5   │ │ }
    4   │ │ flag[i] = c[0];
    3   │ │ recurse(flag, i + 1);
    2   │ │ exit(0);
    1   │ } else {
  135   │ │ waitpid(pid, NULL, 0);
    1   │ }
    2   }

Essentially, this `recurse()` function initialises an `RWX` page, then creates a random seed and encrypts a stored buffer with that random seed. That encrypted shellcode is then placed into the `RWX` page, the binary is forked, and the shellcode is executed with its `stdout` captured in a pipe. This happens 53 times, one for each character of the flag.

The random seed is, of course, random - it is highly likely that whatever shellcode is encrypted is therefore garbage that will cause a segfault and a premature exit. Therefore, the binary will only 'succeed' in printing the flag when the `rand()` calls exactly produce the correct 16-bit key per each iteration of the program, producing shellcode that will print one character to stdout. This is why the binary could technically print the flag if ran enough times, it is just highly, highly unlikely.

Naturally, we would then want to lift the `encrypt()` routine manually and brute-force it with a script. The `encrypt()` method, however, is obfuscated and written with SIMD instructions that is very time consuming to rewrite manually. The approach intended, therefore, is to not reimplement this function at all, and just use an implementation that we already have - the one in the binary.

The important thing to notice is that the `encrypt()` routine does not rely on any external function calls and is entirely self-contained. We can therefore just use the function in our own C code and write a brute-forcer from there. The way I approached it is to `mmap` the binary itself in its own RWX region, and then cast the offset to our `encrypt()` function as a pointer which we can call.

  21   int main() {

closing thoughts

I got the idea for this challenge from a trick I learned from a Flare-On writeup. I think it is neat, but if I were to rewrite this now I would have made the `encrypt()` function more difficult to instrument in this manner. I did actually inline a bunch of the SIMD helper functions and made sure to format the `encrypt()` function in such a way that you could just rip the bytes out like a caveman intentionally to nerf the challenge a bit, but thinking back on it... that's lame! I should have forced players to figure out how to emulate the function with Unicorn and add annoying library functions that you would need to hook. Perhaps I would have also forced emulation of the decrypted shellcode itself, and made the shellcode more difficult to stereotype cleanly with some polymorphic trickery. Damn, this challenge really is super lame... oh well!

As an aside, because the `encrypt()` function is a bunch of ugly SIMD nonsense, I simply assumed that no one in their right mind would rewrite the decryption algorithm (especially not when the alternative is easier and less error-prone). I failed to consider, however, that despite the ugliness, it still lends itself to a relatively clean decompilation which an LLM can handily rewrite into Python, which is what a few solvers did. I am once again defeated by Claire Code.

misc - hyperboros

This challenge is an introduction to Python's interpreter and bytecode format.

  12   import ctypes
  11   
  10   def hyperboros():
   9   │   offset = int(input('offset\n>> '))
   8   │   char = bytes.fromhex(input('char\n>> '))
   7   │   assert len(char) == 1
   6   │   ctypes.memmove(id(hyperboros.__code__) + offset, char, len(char))
   5   
   4   for i in range(1, 1000):
   3   │   hyperboros()

In essence, this program allows the user to dynamically bytepatch the Python bytecode of the `hyperboros()` function 1000 times, with the goal being to patch the function into something that will pop a shell. We can briefly consider what the solution to such a challenge would look like in a C-equivalent program - we would perhaps patch past the function's `ret` and write a simple `execve` shellcode. As we will soon learn, however, a 'simple `execve` shellcode' does not have a Python equivalent. Let us first understand the internals of the Python interpreter and code objects.

The average Python shellcode might look something like `__import__('os').system('/bin/sh')`. In Python's bytecode format, such a function would look like this.

In this `dis` output, the opcode is on the left, the argument is the number on the right, and `dis` helpfully shows us what those arguments would end up resolving to. For example, to get a reference to the `__import__` function, `LOAD_GLOBAL` is called with oparg `1`. To get a reference to the `os` string, we perform `LOAD_CONST`. The key thing here is that these `LOAD` instructions are actually just indices into separate tuple objects, such as the `co_names` tuple and the `co_consts` tuple.

So, just to go through it from the top - if a function wants to call `__import__`, it must have a pre-existing string `__import__` in its `co_names` tuple already. It is therefore not possible to write Python bytecode that, in and of itself, gains access to these useful globals through bytecode and bytecode alone - these strings must exist somewhere in the tuple.

Hence the difficulty of the challenge lies in figuring out how to 'break out' of the Python interpreter and gain references to useful functions. But before we get ahead of ourselves, let us investigate the challenge some more by seeing what existing objects we have references to.

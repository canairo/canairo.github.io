background

The one-gadget. We all know it, we all love it, kind of, probably. Rumor has it that they're called one-gadgets because of how there's probably only one that actually works for any given `libc`. For the uninitiated, a `one-gadget` is a specific location or address inside `libc` that we can return to which will pop a shell provided some register constraints are met. There are existing tools to find these one-gadgets automatically, such as the aptly named `one_gadget`:

(base) wrenches@kitty (/work/project/musl-onegad) > one_gadget libc.so.6
0xe1e6f execve("/bin/sh", r9, r10)
constraints:
  [r9] == ⍉ || r9 == ⍉ || r9 is a valid argv
  [r10] == ⍉ || r10 == ⍉ || r10 is a valid envp

0xff54a posix_spawn(rsp+0x64, "/bin/sh", [rsp+0x38], 0, rsp+0x70, [rsp+0xf0])
constraints:
  [rsp+0x70] == ⍉ || {[rsp+0x70], [rsp+0x78], [rsp+0x80], [rsp+0x88], ...} is a valid argv
  [[rsp+0xf0]] == ⍉ || [rsp+0xf0] == ⍉ || [rsp+0xf0] is a valid envp
  [rsp+0x38] == ⍉ || (s32)[[rsp+0x38]+0x4] <= 0

0xff552 posix_spawn(rsp+0x64, "/bin/sh", [rsp+0x38], 0, rsp+0x70, rbp)
constraints:
  [rsp+0x70] == ⍉ || {[rsp+0x70], [rsp+0x78], [rsp+0x80], [rsp+0x88], ...} is a valid argv
  rbp == ⍉ || {[rbp], [rbp+0x8], [rbp+0x10], [rbp+0x18], ...} is a valid envp
  [rsp+0x38] == ⍉ || (s32)[[rsp+0x38]+0x4] <= 0

0xff557 posix_spawn(rsp+0x64, "/bin/sh", rdx, 0, rsp+0x70, rbp)
constraints:
  [rsp+0x70] == ⍉ || {[rsp+0x70], [rsp+0x78], [rsp+0x80], [rsp+0x88], ...} is a valid argv
  rbp == ⍉ || {[rbp], [rbp+0x8], [rbp+0x10], [rbp+0x18], ...} is a valid envp
  rdx == ⍉ || (s32)[rdx+0x4] <= 0

The way that these `one_gadgets` work, in specific, is that there are existing functions within `libc` that spawn shells by themselves. These functions load a fixed `/bin/sh` address from an area within `libc` itself and then call a helper function, typically `posix_spawn` or `execve`. These gadgets do not require us to load `/bin/sh` ourselves, and typically, the constraints applied on the registers _may already be fulfilled by sheer luck_, thus saving us from the trouble of having to set registers. We can dig deeper into the `one_gadget` output by inspecting the actual instructions at those addresses. We work through one specific example here:

gef> x/10i $libc+0xff557
   0x7ffff7ea3557 <exec_comm+647>:	lea    rdi,[rsp+0x64]
   0x7ffff7ea355c <exec_comm+652>:	mov    r9,rbp
   0x7ffff7ea355f <exec_comm+655>:	xor    ecx,ecx
   0x7ffff7ea3561 <exec_comm+657>:	lea    r8,[rsp+0x70]
   0x7ffff7ea3566 <exec_comm+662>:	lea    rsi,[rip+0xad937]        # 0x7ffff7f50ea4
   0x7ffff7ea356d <exec_comm+669>:	call   0x7ffff7ea11f0 <__GI___posix_spawn>
   0x7ffff7ea3572 <exec_comm+674>:	mov    rdi,QWORD PTR [rsp+0xf0]
   0x7ffff7ea357a <exec_comm+682>:	cmp    rdi,r14
   0x7ffff7ea357d <exec_comm+685>:	je     0x7ffff7ea3584 <exec_comm+692>
   0x7ffff7ea357f <exec_comm+687>:	call   0x7ffff7dcc3d0 <free@plt>
gef> x/s 0x7ffff7f50ea4
0x7ffff7f50ea4:	"/bin/sh"

This gadget places us in the middle of the `libc` function `exec_comm()`, which inevitably calls `posix_spawn()`. Note the key feature here being that `rsi` is pre-loaded with a pointer to a `/bin/sh` string for us automatically, and we have control over most other registers due to the instructions that happen to be there. Hopefully, this example elucidates the actual internal function of a `one_gadget` - we abuse `libc` helper functions that spawn shells, jumping into the middle of function bodies to give ourselves additional control over relevant registers such that our shells spawn successfully. We specifically target the instructions just before the proper function call, affording us as much register control as possible.

The constraints associated with a `one_gadget` are therefore the registers we need to set beforehand such that the function call succeeds. We can look at the above `one_gadget` again, noting that `rdi` points to some address on the stack (`[rsp + 0x64]`), `r8` points to another stack address, `r9` as well. We must therefore understand what registers correspond to which values for our function call. Specifically, for `posix_spawn()`, we have:

  1. `rdi`: `pid_t* pid`. This needs to point to a writable region of memory.
  2. `rsi`: `char* path`. This needs to point to a `/bin/sh` string. The gadget does this for us, so it is no worry.
  3. `rdx`: `posix_spawn_file_actions_t* file_actions`. This needs to be ⍉.
  4. `rcx`: `posix_spawnattr_t* p`. This needs to be ⍉.
  5. `r8` : `char* argv`. This needs to be ⍉.
  6. `r9` : `char* envp`. This needs to be ⍉.

Unfortunately, `posix_spawn()` is very picky when it comes to constraints, and six registers in total need to be set. Compare this with `execve()`, which takes 3, or `system()`, which takes just 1. We are not afforded the luxury of an easily-hijackable `libc` function that calls `system`, though :( We can, however, note that in our gadget above, a lot of these values are already pre-set or inevitably point to values on the stack which we can already control.

gef> x/10i $libc+0xff557
   0x7ffff7ea3557 <exec_comm+647>:	lea    rdi,[rsp+0x64] (RDI is a stack address)
   0x7ffff7ea355c <exec_comm+652>:	mov    r9,rbp (R9 is now RBP)
   0x7ffff7ea355f <exec_comm+655>:	xor    ecx,ecx (RCX is ⍉ed out for us)
   0x7ffff7ea3561 <exec_comm+657>:	lea    r8,[rsp+0x70] (R8 is a stack address)
   0x7ffff7ea3566 <exec_comm+662>:	lea    rsi,[rip+0xad937]        # 0x7ffff7f50ea4 (RSI is /bin/sh)
   0x7ffff7ea356d <exec_comm+669>:	call   0x7ffff7ea11f0 <__GI___posix_spawn>

We can conclude that these register constraints are actually quite easy to fulfill. A stack overflow would provide us the ability to ⍉ out the required fields on the stack, and `RBP` control is typically given for free per each function prologue. Perhaps, even, those values past the stack would already be serendipitously ⍉ed out. Indeed, this specific gadget is quite forgiving, and any significant stack overflow of around 0x80 bytes past the return address is enough here.

A bit of editorializing before the meat of this blog post. Personally, I initially found these one-gadgets inelegant and frustrating, due to how difficult it may be to set these registers properly, and how annoying they are to debug. I've changed my mind on this though! The fact that these even exist are, to me, the height of an endlessly compelling aspect of vulnerability research; that being, the ability to conjure something out of essentially nothing, the ability to use random things in a program and conjure magic out of scraps. It takes a lot of ingenuity to come up with this idea, and it takes the stars aligning for these ideas to even work. To me, there is a lot of beauty in that.
